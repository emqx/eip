# Secure Password Hashing

## Changelog

* 2026-07-15: @savonarola Initial draft

## Abstract

This proposal defines security hardening for MQTT password hashing in EMQX built-in database authentication.
It also improves the storage schema to allow further algorithm changes.

## Motivation

Currently, almost all password hashing algorithms used by EMQX are insecure by default,
including `plain`, `md5`, `sha`, `sha256`, and `sha512`, and for secure algorithms,
such as PBKDF2 or bcrypt, EMQX does not enforce OWASP-recommended minimums.

In the `hardened` profile, EMQX needs secure defaults for new credentials.
Also, we need a safe way to change password hashing settings without breaking existing users.

## Design

### Difficulties

The insecure password hashing algorithms have existed for so long for a reason.

In short,

**We cannot satisfy secure password hashing requirements while flawlessly maintaining high connection rates.**

All secure password hashing algorithms ([OWASP Password Storage Cheat
Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)) are very CPU-intensive.
Applying them in EMQX makes it an easy target for DoS attacks.
Malicious clients can establish connections at a high rate, exhausting server resources.

The following countermeasures were considered:

1. For non-existent clients, do not make an actual secure hash comparison. Implement time padding to mitigate timing attacks (i.e. sleep before responding to authentication requests in a manner that response latency is distributed in the same way regardless of whether we do password checking or not).
2. For existing clients, we implement lockout: after a certain number of failed authentication attempts, the client is locked out for a period of time. That is, we respond with authentication failure after too many unsuccessful attempts.

The downsides of these measures are:

* Sleeping before responding keeps the connection and authentication process alive. An attacker
  may exhaust sockets, memory, timers, or processes instead of CPU.
* Lockout allows an attacker to produce a DoS attack against an individual known account by
  repeatedly trying to authenticate with incorrect passwords.
* A malicious user may distribute attempts across many known account IDs (usernames or client IDs)
  and still produce a DoS attack against the whole system.
* Concurrent authentication attempts may start expensive password checks before the lockout is
  observed.
* Even if we have no attack at all, EMQX can easily experience DoS caused by password hashing.
If valid clients get disconnected at once (which is possible e.g. due to network lags), many clients reconnect
at once and quickly exhaust the server's CPU. A single secure authentication hash is calculated in hundreds of milliseconds, so a commodity server will be exhausted by a few hundred (re)connections per second.

### General Idea

Instead of hardening the hashing algorithms and then fighting the resulting DoS risk, we try to solve the problem by splitting the use cases.

We do not try to satisfy two conflicting requirements at once:
* Hash passwords using OWASP recommendations.
* Flawlessly handle connections from thousands or millions of clients.

Instead, we note that:
* When we need strong hashing for passwords (to avoid dictionary brute-force attacks), we assume that they may have low security and entropy. That is, the passwords are provided manually by humans, in limited numbers.
* When we need to handle connections from numerous clients, these clients are almost certainly provisioned automatically because of their quantity.

So to achieve safe defaults we split these use cases and provide safe defaults for each.

* For *large automated installations*, we treat the password as if it is an API key:
  * we autogenerate safe keys ourselves and provide them on creation, rather than receiving the keys from a user;
  * we use a lightweight hash (e.g. `sha256`) to store autogenerated keys.
* For *small installations with manual password management*:
  * we treat the password as before;
  * we apply OWASP recommendations for the defaults.

By default we assume the first use case.

We do not claim that the use cases do not overlap. By separating the use cases we require users
* either to use the proposed safe default without performance penalty;
* or to switch to providing credentials manually and make choices explicitly.

### Autogenerated Password Format

EMQX generates 32 random bytes using `crypto:strong_rand_bytes(32)` and encodes them
using Base62. The resulting password has 256 bits of entropy.

For autogenerated passwords, EMQX preserves the existing `sha256` password hash format.
It stores the lowercase hexadecimal SHA-256 hash with an empty salt and
`salt_position = disable`.

The plaintext password is returned only in the creation or rotation response and is not
stored by EMQX.

### Password Hashing Settings in User Records

Currently, password hashing settings belong to the authenticator. User records do not contain
the algorithm used to create the password hash. Changing the authenticator settings makes EMQX
use the new algorithm for all existing users, and may make them unable to authenticate.

For new and updated users, we introduce a new `extra` entry, `algo`, containing the complete
password hashing settings used to create the password hash. We create or
update users in the `emqx_authn_mnesia_ns` table, even for the global namespace.

For example, a new user record may look like:

```erlang
#emqx_authn_mnesia_ns{
    user_id = {<<"ns">>, <<"g">>, <<"userid">>},
    password_hash = <<"...sha256...">>,
    salt = <<>>,
    is_superuser = false,
    extra = #{
        algo => {sha256, disable}
    }
}
```

When a user authenticates, EMQX uses the algorithm from the `algo` entry. For old records
where the entry is absent, EMQX uses the password hashing settings from the authenticator, as it
does now. Therefore, changing the settings may still break old users, but users created or
updated after this change continue to work with their recorded settings.

This mechanism is independent of `autogenerate_password`. It is used both for manually
provided and autogenerated passwords.

### Imports and Bootstrap

Plaintext imports, pre-hashed imports, bootstrap files, and bulk imports work as before.
The `autogenerate_password` setting does not force password generation for imported users.

For plaintext imports, EMQX hashes the provided password using the current authenticator settings
and stores these settings in the `algo` entry. For pre-hashed imports, EMQX does not change the
provided password hash or salt. It assumes they match the current authenticator settings, as it
does now, and stores these settings in the `algo` entry.

## Config Changes

We introduce a new setting for built-in authn: `autogenerate_password => boolean()`. The value corresponds to
the described use cases: `false` for manual password management; `true` for automatic generation. The setting only
controls whether a password is provided or generated. Password hashing settings and password verification
are handled separately.

The default value is:
* `false` for legacy profile;
* `true` for hardened profile.

The password hashing settings remain separate from `autogenerate_password`.

The available password hashing settings depend on the profile and the authentication backend:

* in legacy profile, password hashing settings remain unchanged for built-in and external databases;
* in hardened profile, password hashing settings remain unchanged for external databases;
* in the hardened profile and built-in database, `plain`, `md5`, `md4`, and `sha` are not allowed
  as password hashing algorithms or PBKDF2 MAC functions. Explicit `sha256`, `sha512`, and
  other supported settings remain available.

The default value for password hashing is:

* `sha256` for legacy profile;
* `sha256` for hardened profile with `autogenerate_password = true`;
* `pbkdf2` with OWASP-recommended defaults for hardened profile with
  `autogenerate_password = false`.

### OWASP-Recommended PBKDF2 Defaults

The OWASP-recommended defaults used by EMQX are:

* PBKDF2-HMAC-SHA256 with 600,000 iterations;
* PBKDF2-HMAC-SHA384 with 600,000 iterations, using the SHA-256 recommendation;
* PBKDF2-HMAC-SHA512 with 220,000 iterations.

The default for the hardened profile with `autogenerate_password = false` is
PBKDF2-HMAC-SHA256 with 600,000 iterations. These values are defaults only,
not enforced minimums. A user may explicitly configure other supported values.

The salt and derived key length retain the existing EMQX behavior. The salt contains
16 random bytes represented as lowercase hexadecimal, and by default the derived key
length is the output length of the selected MAC function.

So,
* in legacy profile, things remain unchanged.
* in the hardened profile, the default is `sha256` with `autogenerate_password = true`. When a user switches to `autogenerate_password = false`, safe `pbkdf2` is selected by default.

## API and Dashboard Changes

With `autogenerate_password => false` everything works as is.

With the `true` value, the API shape changes for creating users. Instead:
```
POST /api/v5/authentication/password_based%3Abuilt_in_database/users

{
  "user_id": "someuser",
  "password": "somepass",
  "is_superuser": false
}
```
and the response:
```
{
    "namespace": null,
    "is_superuser": false,
    "user_id": "someuser"
}
```

We have:
```
POST /api/v5/authentication/password_based%3Abuilt_in_database/users

{
  "user_id": "someuser",
  "is_superuser": false
}
```
and the response:
```
{
    "namespace": null,
    "is_superuser": false,
    "user_id": "someuser",
    "password": "l2TNFUYle1PkJt0kkL4rgSoJq8n1ssJYVcpySosSmnw"
}
```

To change an autogenerated password, we introduce a separate endpoint:

```
POST /api/v5/authentication/password_based%3Abuilt_in_database/users/someuser/password/rotate
```

The response contains the newly generated password:

```
{
    "namespace": null,
    "is_superuser": false,
    "user_id": "someuser",
    "password": "l2TNFUYle1PkJt0kkL4rgSoJq8n1ssJYVcpySosSmnw"
}
```

Updating other user fields does not rotate the password.

If a create response is lost, the caller may repeat the create request. If EMQX responds
that the user already exists, the caller uses the password rotation endpoint. If a rotation
response is lost, the caller issues another rotation request and uses its response.

GET and list requests never return the password, since EMQX stores only its hash.

In the Dashboard, we show the autogenerated password like many services do in their admin panels with API keys, with a warning that the password is shown once.

### Other Considerations

Whenever a user configures `pbkdf2`, we must warn them in the Dashboard about the possible computational cost of the method.

Since the use-case split defines safe defaults, not the full behavior, in the hardened profile and
`autogenerate_password = false` we still support "insecure" hashes `sha256`, `sha512`, etc.
This allows users to provide their own high-entropy passwords and use CPU-efficient hashing.
For external databases, password hashing settings remain the same as in legacy profile.

## Document Changes

We should separately warn against setting `autogenerate_password = false` in hardened mode and
not checking whether the secure default `pbkdf2` password hashing is appropriate.

Update the built-in database authentication documentation with:

* manually provided and autogenerated password modes, their profile defaults, and the fact that
  the mode does not control password verification;
* one-time password display, password rotation, and recovery when a create or rotation response
  is lost;
* the 32-byte random password format, Base62 encoding, and `sha256` storage format;
* exact PBKDF2 defaults and their expected impact on authentication and reconnect performance;

## Testing Suggestions

Add automated coverage for:

* `autogenerate_password` defaults in legacy and hardened profiles;
* password hashing allowlists for built-in and external databases in both profiles;
* autogenerated password storage as a lowercase hexadecimal SHA-256 hash with an empty salt
  and `{sha256, disable}` algorithm settings;
* password hashing settings stored in `extra.algo` for new and updated users;
* users with `extra.algo` continuing to authenticate after authenticator settings change;
* old records without `extra.algo` using the current authenticator settings;
* global and namespaced users stored and authenticated with their recorded algorithm settings;
* plaintext, pre-hashed, bootstrap, and bulk imports preserving their existing behavior;
* user creation returning an autogenerated password only when enabled;
* password rotation returning a new password and invalidating the previous password;
* repeated create after a lost response returning that the user exists;
* repeated rotation after a lost response returning another valid new password;
* metadata-only user updates not rotating the password;
* get and list responses and stored user records not containing the plaintext password;
* exact PBKDF2 defaults for every supported MAC function.

Add performance tests for simultaneous valid-client reconnects with PBKDF2 defaults and
document the achieved authentication rate on the test hardware.

## Declined Alternatives

* Accept `plain`, `md5`, `md4`, and `sha` at config time in `hardened` mode but log warnings.
  This would allow misconfiguration to go undetected.
* Just set OWASP-recommended `pbkdf2` settings by default in hardened mode. This may silently degrade performance significantly.
